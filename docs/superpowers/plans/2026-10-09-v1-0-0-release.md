# v1.0.0 正式リリースと GitHub Releases 配信の計画

**Goal:** Spica Photo Viewer を正式なバージョン 1.0.0 としてタグ付けし、NSIS インストーラー（`Spica Photo Viewer_1.0.0_x64-setup.exe`）を GitHub Releases で配信して、第三者がリポジトリをビルドせずに使える状態にする。あわせて、以後のリリースがタグを打つだけで再現できる仕組み（GitHub Actions のリリースワークフロー）を整える。

**Scope:** Windows 10/11 x64 の NSIS インストーラーのみ（PROJECT_SPEC「Supported Platforms」に従う）。コード署名・自動更新・winget 等の配布チャネルは 1.0.0 では行わない（§7 参照）。

### 揃っているもの

- `package.json` / `src-tauri/tauri.conf.json` / `src-tauri/Cargo.toml` のバージョンはすべて `1.0.0`。`scripts/sync-version.cjs` が `package.json` を正として他 2 ファイルへ同期し、`npm run build` の先頭で自動実行される。

## 2. 判断事項（着手前に決める）

| 項目 | 推奨 | 理由 |
|------|------|------|
| D1 タグ形式 | `v1.0.0`（`v` + package.json の version） | tauri-action の `__VERSION__` 置換と GitHub の慣例に合う |
| D2 ワークフローの起動方法 | **`v*` タグの push** で Draft Release を作成。加えて **`workflow_dispatch`** で「ビルドだけ（Release を作らない）」を実行できるようにする | タグを打つ前に同じワークフローで成果物を確認できる（§4 Phase 3 のドライラン）。Release を Draft にすることで、ノートの最終確認と公開のタイミングを人が握れる |
| D3 リリースノート | 1.0.0 は **手書き**（機能概要・動作要件・インストール手順・SmartScreen の注記・既知の制限）。1.0.1 以降は GitHub の自動生成ノート（`.github/release.yml` でラベル別に分類、`dependencies` は別節）を下書きにして整える | 初回は差分ではなく「何ができるアプリか」を伝える必要がある |
| D4 Windows CI の範囲 | PR と main の CI に **windows-latest の clippy + test ジョブ**を追加する（フルビルドは行わない）。フルビルドはリリースワークフローと `workflow_dispatch` に限る | G3 を塞ぐ最小コスト。フルビルドは 10〜15 分かかる（onboarding/08）ので PR 毎には重い |
| D5 コード署名 | 1.0.0 では **行わない**。README とリリースノートに SmartScreen の手順を書く | 個人開発での証明書取得・運用コストが大きい。将来の選択肢は §7 に記録する |
| D6 1.0.0 の内容凍結 | §4 Phase 4 の開始時点の main を凍結。Dependabot のメジャー更新は 1.0.0 には入れず、**パッチ/マイナー更新のみ**取り込んでから凍結する | メジャー更新は検証コストが高く、1.0.0 の目的（配信の開始）と無関係 |
| D7 ビルドの再現性 | `npm ci` と `cargo build --locked`（tauri-action の `args: --locked`）を使う | ロックファイルと一致しない状態でリリース成果物を作らない |

## 4. 実施フェーズ

各フェーズは独立した PR にする（レビューしやすく、問題が出たときに切り戻せる）。順序は依存関係に従う: Phase 1・2 は並行可、Phase 3 は Phase 1 の後（成果物のメタデータ確認が目的に含まれるため）、Phase 4・5 は Phase 3 の後。

### Phase 1: リポジトリのメタデータと文書の整備（G4・G5・G9）

**Files:** `src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`、`package.json`、`README.md`、`PROJECT_SPEC.md`、`docs/onboarding/08-development-workflow.md`

- [ ] `Cargo.toml`: `description`（例: "A lightweight, fast image viewer for Windows, inspired by Picasa Photo Viewer"）、`authors`、`license = "MIT"`、`repository`、`homepage` を設定する
- [ ] `tauri.conf.json` の `bundle` に `publisher`、`copyright`（LICENSE と一致させる）、`shortDescription`、`longDescription`、`licenseFile`（`../LICENSE`。NSIS のライセンスページに表示される）、`category`（`Photography`）を追加する。`webviewInstallMode` は既定（`downloadBootstrapper`）のままで良いが、既定であることを明示する
- [ ] `package.json` に `repository` / `homepage` / `license` を追加する（`private: true` は維持）
- [ ] README: `releasess` → `releases`。「Known Issues」の base64 の項を削除（PROJECT_SPEC と整合）。「Tech Stack」の Tauri バージョン表記を固定値から外す。「Installation / For Users」に **動作要件**（Windows 10/11 x64、WebView2 ランタイム: 通常は同梱済み、無ければインストーラーが取得）と **SmartScreen の注記**（「詳細情報」→「実行」）を追加する。「Building」の節にリリース手順（§6）への参照を足す
- [ ] PROJECT_SPEC: Phase 4 の「MSI installer」を「NSIS installer」に修正。「Build & Deployment」に「Release」小節を追加し、タグ push によるリリースの流れを 3〜4 行で書く
- [ ] onboarding/08 の「リリースビルド」に、CI でのリリース（§6）への参照を 1 段落追加する
- [ ] 検証: `npm run tauri build` がローカルで通ること。生成された exe のプロパティ（説明・著作権・製品名）と、インストーラーの発行元・ライセンスページの表示を目視で確認し、意図した文言になっていること

### Phase 2: Windows の clippy + test を CI に追加（G3）

**Files:** `.github/workflows/ci.yml`

- [ ] `backend-tests-windows` ジョブを追加する: `windows-latest`、`dtolnay/rust-toolchain@stable`（`components: clippy`）、`Swatinem/rust-cache@v2`（`workspaces: src-tauri`）、`cargo clippy --all-targets -- -D warnings`、`cargo test --lib`。`cargo fmt --check` は ubuntu 側で済んでいるので重複させない
- [ ] 既存の `paths-ignore` をそのまま継承する（文書のみの変更で Windows ランナーを回さない）
- [ ] 検証: このジョブが PR で緑になること。所要時間を記録し、キャッシュが効いた 2 回目以降の時間も確認する（目安を超えるなら D4 を見直す）
- [ ] 併せて、Dependabot の `actions/checkout@7` / `actions/setup-node@7` の PR を取り込むか判断する（ワークフローを触るこの PR で揃えるのが自然）

### Phase 3: リリースワークフローの作成とドライラン（G2・G1 の準備）

**Files:** `.github/workflows/release.yml`、`.github/release.yml`

- [ ] `release.yml` を作成する
  - `on: push: tags: ['v*']` と `on: workflow_dispatch`（入力 `publish: boolean`、既定 false）
  - `permissions: contents: write`
  - `runs-on: windows-latest`、`actions/checkout`、`actions/setup-node`（node 22）、`dtolnay/rust-toolchain@stable`、`Swatinem/rust-cache@v2`、`npm ci`
  - **バージョン整合ガード**: タグ名（`v` を除く）と `package.json` / `tauri.conf.json` / `Cargo.toml` の version が一致しなければ失敗させる。`workflow_dispatch` のときはタグ比較を省き、3 ファイルの一致だけ確認する
  - ビルドと Release 作成は `tauri-apps/tauri-action@v0` を使う: `tagName: ${{ github.ref_name }}`、`releaseName: 'Spica Photo Viewer v__VERSION__'`、`releaseDraft: true`、`prerelease: false`、`args: --locked`。`workflow_dispatch` 時は Release を作らず `actions/upload-artifact` で成果物を保存する（`tauri-action` の Release 作成を `if:` で切る）
  - `SHA256SUMS.txt` を生成して Release / artifact に添付する（PowerShell の `Get-FileHash` で十分）
  - 注意点（コメントとして残す Why）: `beforeBuildCommand` が `sync-version` を実行するため、ガードで一致を確認しておけば CI 上でファイルが書き換わることは無い。NSIS は Tauri CLI がビルド時に取得するので追加のインストール手順は不要
- [ ] `.github/release.yml` を作成し、自動生成ノートの分類（Features / Bug Fixes / Performance / Documentation / Dependencies）をラベルで定義する。1.0.0 では使わず 1.0.1 以降の下書き用（D3）
- [ ] **ドライラン**: `workflow_dispatch` で実行し、artifact のインストーラーをダウンロードして §5 のチェックリストを通す。ビルド時間と成果物サイズを記録する
- [ ] ドライランの成果物で Phase 1 のメタデータ（発行元・説明・ライセンスページ）がローカルビルドと同じであることを確認する

### Phase 4: 内容凍結とリリース候補の検証（G6・G7・G8）

- [ ] Dependabot の PR を整理する（D6）: パッチ/マイナーは取り込む。メジャー更新は 1.0.0 後に回す旨をコメントして残す（close はしない）

## 6. 以後のリリース手順（定常運用。README / PROJECT_SPEC から参照される）

1. `npm version patch|minor|major --no-git-tag-version` で `package.json` を更新し、`npm run sync-version` で 3 ファイルを揃える
2. `chore(release): v1.0.1` のようなコミットを PR 経由で main に入れる（CI 緑を確認）
3. main で `git tag -a v1.0.1 -m "Spica Photo Viewer v1.0.1"` → `git push origin v1.0.1`
4. `release.yml` が Draft Release を作る。自動生成ノート（`.github/release.yml` の分類）を下書きに本文を整え、Publish する
5. パフォーマンス関連の変更を含むリリースでは、CLAUDE.md のルール通り `npm run bench` の結果と `baseline.json` の更新が同じリリースに含まれていることを確認する

## 7. 1.0.0 のスコープ外（記録のみ。着手するなら別のスペック・計画を起こす）

- **コード署名**: SmartScreen の警告を無くすには EV/OV 証明書、Azure Trusted Signing、または OSS 向けの SignPath Foundation などが選択肢。`tauri.conf.json` の `bundle.windows.certificateThumbprint` / `signCommand` で組み込める。配布実績（ダウンロード数）が積まれると警告は自然に弱まる面もある
- **自動更新**: `tauri-plugin-updater` と `latest.json` の配信。署名鍵の管理が必要になる
- **配布チャネル**: winget（`microsoft/winget-pkgs` へのマニフェスト）、Scoop。GitHub Releases の URL が安定してから検討する
- **CHANGELOG.md のリポジトリ内管理**: 1.0.x では GitHub Releases のノートを正とし、必要になったら `git-cliff` などで生成する
- **ARM64 Windows ビルド**: 需要が確認できてから
- **Linux / macOS**: PROJECT_SPEC の対象外。`#[cfg(windows)]` 依存の機能（Explorer の並び順連携、ウインドウ配置）が前提のため、対応するなら設計から

## 8. リスクと対処

| リスク | 対処 |
|--------|------|
| Windows ランナーでのビルドがローカルと異なる（NSIS の取得失敗、ツールチェーン差） | Phase 3 のドライランで先に潰す。失敗時のログは Release を作らない `workflow_dispatch` 側で安全に再現できる |
| タグを打った後にバージョン不一致や成果物の不備が見つかる | Release は Draft で作るので公開前に止められる。やり直す場合はタグを削除して同名で打ち直すのではなく、修正を入れて `v1.0.1` にする（公開済みタグの付け替えはしない。Draft のまま破棄する段階ならタグの削除は許容） |
| `#[cfg(windows)]` 配下の変更が CI をすり抜けて 1.0.0 に入る | Phase 2 を Phase 4 より前に完了させる |
| SmartScreen 警告で第三者が実行を断念する | README とリリースノートに手順とハッシュ（`SHA256SUMS.txt`）を載せる。署名は §7 で追う |
| Dependabot のメジャー更新を取り込んで検証が破綻する | D6 で凍結する。凍結後に来た更新は 1.0.1 以降 |
